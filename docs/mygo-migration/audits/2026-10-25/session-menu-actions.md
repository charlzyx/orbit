# Session row menu and live deletion protection — unreleased increment

Reference: pinned Rust `299a32bc87fe3d4851bdb902d9c03dcf9bf99cac`, `crates/orbit-pi/src/app/sidebar.rs:1249–1395` (menu actions/state labels), `:2167–2192` (copy/reveal), `:2231–2250` (confirmation-time live guard), `:883` (row-menu delete eligibility).

- Pin/archive labels reflect row state and use existing translations. Add Copy path and Reveal actions with the selected row's exact path.
- Preserve Go's Rename and Copy session ID convenience entries. The latter previously dispatched an unhandled `CopySessionId` action with a path; it now dispatches `CopyText` with the row ID.
- Hide Delete for the active runtime and for parked entries that are alive, loading, busy or stopping. Confirmation remains mandatory for eligible saved files, and backend rechecks runtime ownership after confirmation. It no longer implicitly terminates active/parked children to delete their file.
- Reserve the target path under the manager lock during asynchronous deletion so a concurrent `Open` cannot create a runtime between ownership validation and filesystem mutation. No filesystem I/O runs under that lock. Existing recoverable backup behavior is retained rather than adopting Rust's permanent-delete-only implementation.

Tests use temporary files and synthetic runtime entries, never user sessions. Actual mounted menus failed on the previous implementation for missing state labels and live delete eligibility; the new menu passes. Backend regressions preserve active/parked file bytes and selection, reject Open during a reserved deletion, and retain the existing backup/unrelated-file test. These are bounded local checks, not complete session lifecycle or native desktop acceptance. Metadata pruning and workspace-group menu completeness remain separate gaps. Rust’s palette path can arm the active session despite the stricter row-menu eligibility; Go deliberately protects the active runtime at the backend too. Truly quiescent stopped/failed background entries remain deletable: reservation excludes a concurrent reopen, and successful file deletion evicts only those closed entries, preserving the current task. This is a conservative safety difference, not an assertion that every Rust deletion entrypoint is identical.
